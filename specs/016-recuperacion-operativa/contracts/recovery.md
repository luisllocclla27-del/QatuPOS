# Contrato local de recuperación v1

No HTTP de backup/restore. Operador de confianza ejecuta CLI manual fuera del servicio. `pnpm operational:backup` requiere DATABASE_URL, QATU_BACKUP_KEY_FILE, QATU_BACKUP_FILE y QATU_GUEST_KEY_FILE (o ruta estable existente según modo); QATU_PG_BIN_DIR opcional, default binarios locales17.11. `pnpm operational:restore-verify` requiere QATU_RESTORE_DATABASE_URL, QATU_BACKUP_KEY_FILE y QATU_BACKUP_FILE. No acepta datos del navegador. Configuración operativa se carga solo si modo production explícito; no imprimir env/errores crudos del motor.

## Contenedor binario

`QATUBK01` (8 bytes), IV12 bytes, ciphertext, tagGCM16 bytes. MAGIC es AAD. Plaintext: longitud manifest uint32BE, manifest JSON UTF8, archive PostgreSQL custom. Manifest cerrado: format_version=1, backup_id UUID, created_at ISOUTC, source_database (sin host/credenciales), server_major=17, guest_key (base64 de32 bytes o null si no hay guest_access), tables [{name,rows,sha256}]. No se incluyen roles globales ni configuración OS/certificados TLS. JSON limitado2MiB y archive512MiB; superar límite aborta, no deja copia utilizable. Tabla de fingerprints usa nombres SQL reales, fila JSONB normalizada por PostgreSQL y orden C del texto; hashSHA256 de cada JSON UTF8 seguido LF. Se incluyen todas las tablas de usuario de public; schemas extra se rechazan en este piloto para evitar respaldos parciales.

Backup key: exactamente32 bytes binarios, archivo regular sin symlink; no generado implícitamente. Guest key: exactamente32 bytes, no generar si falta con accesos persistidos. Fuente compatible runtime y server17; transacción consistente con export snapshot. Salida `.qatubak` nueva, no overwrite, key/output distintos y no mismo directorio. Operativo: fuera del checkout, ACL Windows obligatoria a cargo del instalador (mode600 no demuestra ACL). Clone/manipulación offline con permisos de superusuario queda fuera de certificación.

Destino: PostgreSQL loopback existente, database `qatupos_restore_[a-f0-9]{32}` vacío sin tablas/esquemas de usuario. No DB de origen ni qatupos_lab/qatupos_prod. Configuración de conexión PG sin URL en argumentos, password solo entorno del hijo, protocolo PostgreSQL y TLS para origen remoto verificado. pg_dump/restore17 y server17. Prohibidos clean/create/table selectivo. Autenticar completo y validar manifest/archive antes de abrir transacción de restauración. Destino rechazado con objetos o conexiones ajenas activas; el operador mantiene aislamiento de su rol/puerto.

Resultado JSON seguro: backup_id,created_at,tables_verified,session_counts_revoked,quarantine=true; nunca guest_key/URL/filas. Comparar todas las tablas antes de revocar staff_sessions y guest_sessions; diferencias abortan informe exitoso. Estado y retenciones permanecen exactamente como el snapshot. Restore repetido a esa DB ya poblada rechazado. No hay mecanismo de promoción; operaciones HTTP bloqueadas503 RECOVERY_QUARANTINE y configuración runtime rechaza namespace.

La clave QR debe coincidir con todas las credenciales activas usando la derivación canónica; una clave existente pero equivocada también aborta la copia. `staff_sessions` se eliminan; `guest_sessions` se marcan revocadas, conservando IDs referenciados por cotizaciones y dedupe. No borrar esas relaciones para revocar acceso. Solo restaurar copias generadas por este operador y origen de confianza: PostgreSQL ejecuta el SQL del archivo, por lo que autenticidad criptográfica no acredita un origen malicioso.

Health existente200 conserva status/environment cuando DB sana;503 DATABASE_UNAVAILABLE o RECOVERY_QUARANTINE con mensaje seguro. day.open mismo request existente: operativo409 DAY_DATE_NOT_ADVANCED si fecha Lima <= fecha cerrada. Perfil/password409 IDENTITY_PROJECTION_MISMATCH si membership SQL falta; rollback total. Sin ampliación de permisos.

Antes de restaurar, el operador propietario de la DB permite escribir su comentario persistente `QatuPOS recovery quarantine v1`; ese marcador queda también si el restore falla y se conserva al renombrar la base. El runtime comprueba nombre y comentario en cada admisión. Backup rechaza fuentes con marcador, aunque hayan sido renombradas a un nombre válido. Ninguna herramienta del piloto elimina el marcador; un administrador PostgreSQL puede manipular metadatos con sus privilegios, lo cual requiere procedimiento y revisión de cambio de autoridad, no está certificado ni autorizado por este ensayo.
